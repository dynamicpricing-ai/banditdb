Decision Memory & Storage for AI Agents

BanditDB is an in-memory database that lets your agents learn, adapt and improve with every outcome. Stores (context, action, reward) and computes the best action for each context.

create a campaign 
from banditdb import Client

db = Client("http://localhost:8080")

db.create_campaign(
    "checkout_offer",
    arms=["discount", "free_shipping", "gift"],
    feature_dim=4,
)

  arms: ["discount", "free_shipping", "gift"],
  feature_dim: 4,
});

# context can be an embedding — the DB learns the projection
from banditdb import Client, NeuralLinUCBConfig

01 · architecture

The decision layer

Pluggable infrastructure: one more store next to Postgres and your vector DB, reachable over HTTP. Each layer answers a different query.

stack.txt 
  your app / agents
        │
        ├── SQL ──────────►  postgres       facts        "what is true?"
        ├── embed + ANN ──►  vector store   meaning      "what is similar?"
        └── predict/reward ►  banditdb       policy       "what should I do?"

  swap any layer independently · plain HTTP · no coupling between stores
relational vector store banditdb
write unit row embedding prediction-action-reward tuple
read query SQL predicate nearest neighbour context vector → argmax score
internal state B-tree / heap pages HNSW / IVF index d×d covariance + weight vectors per arm
state size O(rows) O(documents) O(arms · d²) — constant in traffic
answers "what is true?" "what is similar?" "what should I do?"
02 · why not context-stuffing

Transcripts remember what happened.
Confidence remembers what worked.

Every repeated decision an agent re-reasons through an LLM costs tokens, latency, and money — and resets to zero next session. A posterior is the same experience, already paid for.

✗ What you never build again
  • — Hand-rolled Sherman-Morrison updates, hoping the covariance matrix doesn't go ill-conditioned silently
  • — Reward-attribution plumbing — joining outcomes back to decisions with timing windows
  • — Exploration/exploitation tuning nobody on the team actually understands
  • — The 2 a.m. class of bugs: counters zeroing after a migration, state drift after restarts
  • — Re-validating all of it every time the model or feature set changes
03 · storage model

Matrices, not documents

Diagonal decays as evidence accumulates — tight diagonal = confident arm. Optional per-campaign half-life re-inflates it, so the policy forgets under drift.

update path
O(d²) · µs 
# per reward — no retraining, no batch job
# Sherman-Morrison rank-1 update:
#
#   A_inv -= (A_inv·x)(xᵀ·A_inv) / (1 + xᵀ·A_inv·x)
#   b     += reward * x
#   theta  = A_inv · b        # exact, closed form
#
# symmetry re-enforced each step:
#   A_inv = (A_inv + A_invᵀ) / 2

No gradient descent on the hot path. Neural variants (NeuralLinUCB, NeuralThompsonSampling) add an MLP embedding retrained off-path at checkpoints — the matrix store underneath is identical.

04 · operations

Monitoring · backup · restore

Learned state is production state. Observable over HTTP, durable through WAL + checkpoints, recoverable after a crash.

01 · monitoring

Observable

Prometheus metrics, per-campaign diagnostics (θ norms, covariance diag bounds, tournament state), entropy alerting for exploration collapse.

GET /metrics
GET /campaign/:id/diagnostics
GET /campaign/:id/report
GET /health → ok | degraded
02 · backup

Durable

WAL before memory on every write. Checkpoints snapshot matrix state, export tuples to Parquet, rotate the WAL. Auto-triggered by event count or WAL size.

POST /checkpoint
BANDITDB_CHECKPOINT_INTERVAL
BANDITDB_MAX_WAL_SIZE_MB
03 · restore

Recoverable

Startup loads the last checkpoint and replays the WAL from its offset. Process dies, policy survives. Campaigns archive/restore without state loss.

recover() — automatic on boot
POST /campaign/:id/archive
POST /campaign/:id/restore

05 · mcp server

Shared policy state for agent fleets

Stateless agents repeat yesterday's mistakes. The MCP server exposes campaigns as tools, so every agent reads and writes one shared, persistent policy.

banditdb-swarm · NeuralLinUCB 
$ banditdb-swarm --agents 3 --campaign prompt_strategy --algo neural

Two commands and BanditDB is a native tool in Claude, Cursor, or any MCP-compatible host. Agents can get intuition, record outcomes, and inspect learning state — no config file editing required.

Every decision made by any agent updates the shared policy for all future agents. The fleet accumulates a policy no single agent could learn alone.

Not a chat memory, not a vector store — a decision layer that learns which choices work for which context, one recorded outcome at a time.
